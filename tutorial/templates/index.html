01GET

"I want to read something, and I want the result to be safe to repeat."

What is it

GET retrieves a representation of the resource at the given URI. It is safe (no side effects) and idempotent (calling it 10 times produces the same result as calling it once).

Why it exists

Every website in the world starts with a GET. Search engines, browsers, and CDNs are built on the assumption that GET does not change anything on the server. That assumption is what makes caching, prefetching, and link-sharing safe.

Try it — with curl

Terminal
curl -i "http://192.168.10.7:5000/demo/get?name=alice&role=admin"

What you'll see

HTTP/1.1 200 OK
Server: Werkzeug/3.1.5 Python/3.13.12
Content-Type: application/json

{
  "query_params": { "name": "alice", "role": "admin" },
  "_method_reached": "GET",
  "_client_ip": "192.168.10.7",
  "_user_agent": "curl/8.x.x"
}

What to notice

  • The query string is broken out into individual parameters.
  • The server echoes the method it saw — GET.
  • The query parameters are visible in the URL. They show up in server logs, browser history, and the Referer header on any link a user clicks next.

Burp equivalent

  1. Open Firefox through Burp (proxy on).
  2. Visit http://192.168.10.7:5000/demo/get?name=alice&role=admin.
  3. In Burp: Proxy → HTTP History. Find the GET request.
  4. Right-click → Send to Repeater. Change the name value and hit Send.
Attack surface: Never put secrets in a query string. Tokens, session IDs, passwords — all logged by reverse proxies, CDNs, and the browser itself.

02POST

"I want to send data to the server and have it do something."

What is it

POST submits data to be processed. It is not safe and not idempotent — submitting the same form twice may create two records.

Why it exists

GET puts everything in the URL. That's fine for a search query, terrible for a 10 MB file upload or a password. POST moves the data into the request body, separate from the URL.

Try it — with curl

Terminal
curl -i -X POST http://192.168.10.7:5000/demo/post \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "name=alice&role=admin"

What you'll see

HTTP/1.1 200 OK
Content-Type: application/json

{
  "form_data": { "name": "alice", "role": "admin" },
  "json_body": null,
  "raw_body": "name=alice&role=admin",
  "content_type": "application/x-www-form-urlencoded",
  "_method_reached": "POST",
  "_client_ip": "192.168.10.7"
}

What to notice

  • The data is in the body, not the URL.
  • Content-Type tells the server how to parse it. Change it to application/json and the server parses JSON instead.
  • Body content does not appear in server access logs by default — safer for secrets, but still visible in the browser's dev tools and any proxy in between.

Burp equivalent

  1. Send the curl request above, then find it in Proxy → HTTP History.
  2. Right-click → Send to Repeater.
  3. In the Repeater request pane, edit the body below the blank line and resend.
Note: Many frameworks only apply CSRF protection to POST. Methods like PUT and DELETE often slip past that protection — the basis of the challenge lab.

03PUT

"I want to replace the entire resource at this URI."

What is it

PUT replaces the resource wholesale. Idempotent — sending the same PUT twice leaves the resource in the same final state.

Why it exists

REST needed a "full replace" verb distinct from "partial update." PUT is what you'd use when uploading a file to a known URL: whatever was there before is gone, replaced by what you sent.

Try it — with curl

Terminal
curl -i -X PUT http://192.168.10.7:5000/demo/put \
  -H "Content-Type: application/json" \
  -d '{"name":"alice","role":"admin","balance":9999}'

What you'll see

HTTP/1.1 200 OK
Content-Type: application/json

{
  "raw_body": "{\"name\":\"alice\",\"role\":\"admin\",\"balance\":9999}",
  "note": "PUT semantically means REPLACE the whole resource.",
  "_method_reached": "PUT"
}

What to notice

  • The server received your JSON body intact — no form parsing.
  • PUT assumes the client is authorized to overwrite this URI. If the auth check is missing, an attacker can overwrite other users' data.

Burp equivalent

  1. In HTTP History, find the PUT request.
  2. Send to Repeater. Change the body — for example, set "role":"user" to "role":"admin" and resend.
  3. Watch how the server accepts anything you send. That's the vulnerability in the wild.
Attack surface: Missing authorization on PUT = arbitrary data overwrite. This is the classic "horizontal privilege escalation" bug.

04PATCH

"I want to change one field, not the whole object."

What is it

PATCH applies partial modifications. Not necessarily idempotent — depends on the patch format (JSON Merge Patch, JSON Patch, etc.).

Why it exists

Sending an entire user record just to change a phone number wastes bandwidth. PATCH was standardized in RFC 5789 (2010) so clients could send only the diff.

Try it — with curl

Terminal
curl -i -X PATCH http://192.168.10.7:5000/demo/patch \
  -H "Content-Type: application/json" \
  -d '{"role":"admin"}'

What you'll see

HTTP/1.1 200 OK
Content-Type: application/json

{
  "raw_body": "{\"role\":\"admin\"}",
  "note": "PATCH semantically means apply a PARTIAL update.",
  "_method_reached": "PATCH"
}

What to notice

  • You sent one field. A well-behaved PATCH handler would only touch that field.
  • A badly behaved handler that blindly merges the input into the user object will set your role to admin — even though the legitimate client only sends {"email":"..."}.

Burp equivalent

  1. Intercept a normal profile-update request in your own test app.
  2. Send it to Repeater. Add "role":"admin" to the JSON body.
  3. Send. If the server accepts it, you've just exploited a mass-assignment vulnerability.
Attack surface: Mass assignment. PATCH endpoints are the #1 place this shows up because developers treat the body as a "partial update" and merge everything without a whitelist.

05DELETE

"I want to remove the resource."

What is it

DELETE removes the resource at the given URI. Idempotent — deleting something that's already gone should return the same success response, not an error.

Why it exists

REST needed a removal verb that doesn't require a body. DELETE maps naturally to database deletes, file removals, and token revocation.

Try it — with curl

Terminal
curl -i -X DELETE "http://192.168.10.7:5000/demo/delete?id=42"

What you'll see

HTTP/1.1 200 OK
Content-Type: application/json

{
  "note": "DELETE removed a resource (simulated).",
  "would_delete_id": "42",
  "_method_reached": "DELETE"
}

What to notice

  • No body needed — the target resource is identified entirely by the URL.
  • Many CSRF frameworks only check POST. If DELETE uses cookie-based auth with no CSRF token, a malicious page can trigger deletes on a victim's behalf.

Burp equivalent

  1. In Repeater, change the method of a POST request to DELETE and remove the body.
  2. Send. Observe whether the endpoint still performs the action.
  3. Try sending DELETE without a CSRF token — that's what an attacker would do.
Attack surface: CSRF via non-POST methods. Modern frameworks like Django and Laravel now enforce CSRF on all state-changing methods, but plenty of custom code doesn't.

06HEAD

"Give me the same response as GET, but skip the body."

What is it

HEAD is GET without the response body. The status line and headers are identical to what GET would return.

Why it exists

A download manager wants to know the file size before it starts the download. A link checker wants to know if a page exists without transferring the HTML. HEAD is the efficient answer to both.

Try it — with curl

Terminal
curl -I http://192.168.10.7:5000/demo/head

What you'll see

HTTP/1.1 200 OK
Server: Werkzeug/3.1.5 Python/3.13.12
X-Method-Reached: HEAD
X-This-Would-Be-Body: If this were GET, this would be the body content
X-Auth-Check-Note: Handlers that only block GET miss this entirely
Content-Type: text/html; charset=utf-8
Content-Length: 0

What to notice

  • No body, but the headers are real.
  • Your custom X-* headers survive — that's how you exfiltrate data from HEAD in the challenge lab.
  • Any server-side logic in the GET handler still ran. If it checks admin status after the method check, HEAD bypasses it.

Burp equivalent

  1. Send the HEAD request with curl, then look in HTTP History.
  2. Click the entry. The response pane shows headers only — no body.
  3. Right-click the request → Change request method → Burp lets you switch between GET, POST, HEAD, and others.
Attack surface: Method-based authorization bypass. The single most common bypass is a developer writing if method == "GET": require_auth(). HEAD sails past.

07OPTIONS

"What can I do to this resource?"

What is it

OPTIONS returns the methods the server supports for the given resource, usually in an Allow header.

Why it exists

Before a browser sends a cross-origin PUT with a custom header, it asks the server "would you accept this?" via an OPTIONS request. That's CORS preflight. OPTIONS is how the browser learns the rules.

Try it — with curl

Terminal
curl -i -X OPTIONS http://192.168.10.7:5000/demo/options

What you'll see

HTTP/1.1 204 NO CONTENT
Allow: GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS
Content-Length: 0

What to notice

  • The Allow header is the full inventory of methods this endpoint accepts.
  • Reconnaissance. Before you send a single exploit, you now know the entire attack surface.
  • If TRACE shows up in that list, you have a finding on any production server.

Burp equivalent

  1. Send to Repeater. Change the method line to OPTIONS /endpoint HTTP/1.1.
  2. Send. Read the response headers.
  3. Intruder tip: place § around the method and fire all eight methods against the same URL to map the endpoint.
Methodology: Always OPTIONS first. It's free, it's fast, and it maps your attack surface before you waste time guessing.

08TRACE

"Echo my request back to me — headers and all."

What is it

TRACE returns the exact request the server received, as the response body. It's a debugging tool for proxy chains.

Why it exists

Historically useful when debugging what a proxy did to a request — did it add a Via header? Strip Authorization? Rewrite Host? TRACE showed you. Modern servers disable it because it's not worth the risk.

Try it — with curl

Terminal
curl -i -X TRACE http://192.168.10.7:5000/demo/trace \
  -H "Authorization: Bearer super-secret-token" \
  -H "X-Custom: hello-from-curl"

What you'll see

HTTP/1.1 200 OK
Content-Type: message/http

TRACE /demo/trace HTTP/1.1
Host: 192.168.10.7:5000
User-Agent: curl/8.x.x
Accept: */*
Authorization: Bearer super-secret-token
X-Custom: hello-from-curl

What to notice

  • The entire request is echoed back — including the Authorization header you sent.
  • If an attacker has any way to make the browser issue a TRACE (XSS via fetch), they can read back HttpOnly cookies and auth headers.
  • This is Cross-Site Tracing (XST), documented since 2003.

Burp equivalent

  1. In Repeater, change the method to TRACE.
  2. Add an Authorization header with a fake value.
  3. Send. The response body is the request you just sent — headers included.
Attack surface: Cross-Site Tracing (XST). Disable TRACE at the server or framework level. Flask, Express, nginx, and Apache all support disabling it.
